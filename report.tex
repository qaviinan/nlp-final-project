\section{1. Methodology}
% ─────────────────────────────────────────────────────────────────────────────

\subsection{1.1 Overview}
This project fine-tunes Llama-3.1-8B via Low-Rank Adaptation (LoRA) to improve performance simultaneously on instruction following (IFEval), math reasoning (GSM8K), and code generation (HumanEval). All training used the Tinker API with supervised fine-tuning (SFT) as the primary method, followed by a reinforcement learning stage using a custom GRPO implementation.

\subsection{1.2 Model and LoRA Configuration}
Base model: \texttt{meta-llama/Llama-3.1-8B}. LoRA rank 128 applied to all layer types (attention, MLP, unembedding). Renderer: \texttt{role\_colon}.

\subsection{1.5 Training Procedure}
Training ran in two phases. Phase 1: 8,000 steps from a randomly initialized LoRA adapter, checkpointing every 1,000 steps. Phase 2: resumed from the step-8000 checkpoint via \texttt{create\_training\_client\_\allowbreak from\_state} with lr=3e-5 and a different random seed to sample fresh examples. Intermediate checkpoints were evaluated to identify the optimal stopping point.

\section{2. Extensions}
% ─────────────────────────────────────────────────────────────────────────────

\subsection{2.1 Constraint Failure Analysis and Targeted Dataset Selection}
Rather than treating IFEval as monolithic, we performed programmatic constraint-level analysis on evaluation logs using the \texttt{instruction\_following\_eval} library. This revealed three failure buckets: case constraints (95--100\% failure: \texttt{english\_lowercase}, \texttt{english\_capital}), length/count constraints (79--100\% failure: \texttt{number\_words}, \texttt{number\_sentences}, \texttt{number\_paragraphs}), and keyword constraints (81--84\% failure: \texttt{forbidden\_words}, \texttt{frequency}). Armed with this diagnosis, we identified \texttt{argilla/ifeval-like-data} (filtered): 56,339 examples generated by Qwen2.5-72B-Instruct and verified against the IFEval constraint checker. Replacing Tulu-3 with this dataset produced an 18-point IFEval jump (41.9\% $\to$ 60.2\%), the largest single improvement of the project.

\subsection{2.2 Manual GRPO on an SFT-Only API}
Tinker does not natively support RL, so we implemented GRPO using available primitives. Each step: (1) sample a prompt from argilla; (2) generate $G{=}16$ responses via \texttt{create\_sampling\_client} at temperature 1.0; (3) score each with partial credit reward (fraction of constraints passing); (4) compute group-relative advantages $A_i = (r_i - \bar{r}) / (\sigma_r + \epsilon)$; (5) create weighted datums for positive-advantage outputs scaled by $A_i$; (6) \texttt{forward\_backward} + \texttt{optim\_step}. Key engineering challenges included discovering that \texttt{build\_generation\_prompt} returns \texttt{ModelInput} directly, that \texttt{SampledSequence} exposes \texttt{tokens} not text, and that stop sequences prevent the model from generating fake multi-turn continuations. GRPO showed modest gains on GSM8K (+0.7\%) and HumanEval (+0.6\%) with no IFEval regression, demonstrating successful multi-task RL without catastrophic forgetting.

\subsection{3.2 Intermediate Checkpoint Analysis}
We evaluated checkpoints every 1,000 steps during v5 training. The loss curve showed continued decline throughout all 8,000 steps (avg loss: 0.422 at step 1000, 0.395 at step 5000, 0.364 at step 8000), with no sign of convergence or overfitting. GSM8K improved monotonically from 56.7\% at step 3000 to 68.3\% at step 8000. IFEval peaked at step 5000 (63.5\%) and declined slightly at step 8000 (63.0\%), suggesting modest task-specific overfitting for constraint following. HumanEval peaked at step 8000 (45.7\%). This confirms the professor's warning that the final checkpoint is not always optimal: for a competition submission maximizing average score, step 8000 is best overall, but a practitioner optimizing IFEval specifically should prefer step 5000. We used step 8000 as the submission checkpoint.

\subsection{3.3 What Worked}
The argilla dataset selection was by far the most impactful intervention. Scaling to 8B gave large gains on all tasks. Chain-of-thought prefixes improved GSM8K substantially. Continued training beyond 2,000 steps produced meaningful improvements --- the loss curve had not converged, and scores improved monotonically through 8,000 steps.

\subsection{3.4 What Did Not Work}
Adding a system prompt to all Tulu examples (v3) caused a 3-point IFEval regression. Post-hoc constraint analysis confirmed it made every constraint category worse, likely because the system prompt caused the model to prepend constraint-checking preambles that violated prompt-level strict scoring. Generic Tulu data showed rapidly diminishing returns beyond 50k examples for mechanical constraint types --- the model learned general conversational instruction following but could not generalize to verifiable surface constraints. GRPO produced limited IFEval improvement due to sparse reward signal: at 60\%+ accuracy, most prompts yield identical rewards across all $G$ samples, producing no gradient update.

\subsection*{Tinker Platform Feedback}

\textbf{Hardest part.} The gap between the SFT-oriented API and advanced training methods. Implementing GRPO required significant reverse-engineering: discovering that \texttt{save\_state} (not \texttt{save\_weights}) is needed for resumable checkpoints, that sampler weights and training weights use different path formats, and that \texttt{create\_training\_client\_from\_state} does not accept sampler paths. Better documentation of the checkpoint path format taxonomy would have saved considerable debugging time. Windows compatibility was also a persistent issue --- SSH key setup, HuggingFace Hub symlink warnings, and PowerShell differences from bash all required undocumented workarounds.

\textbf{Tinker-cookbook usage.} Yes, extensively. The cookbook was essential for conversation rendering (\texttt{get\_renderer}, \texttt{build\_generation\_prompt}), tokenization (\texttt{get\_tokenizer}), and datum construction (\texttt{conversation\_to\_datum}, \texttt{TrainOnWhat}). What was missing was documentation on \texttt{build\_generation\_prompt}'s return type --- it returns a \texttt{ModelInput} directly rather than tokens, which was not obvious and caused the GRPO prompt rendering to fail initially. Type annotations or a short docstring would have helped.

\textbf{One improvement.} Native GRPO or PPO support. The verifiable reward paradigm is a natural fit for Tinker's API --- the platform already has all the necessary primitives but combining them for RL requires substantial undocumented engineering. A \texttt{grpo\_training\_client} analogous to \texttt{create\_lora\_training\_client} that handles the sampling loop, advantage computation, and reference model KL penalty internally would dramatically lower the barrier to RL experimentation, which the project documentation explicitly encourages.

\textbf{Would you use Tinker again?} Yes. The ability to run large-scale 8B training jobs through a simple Python API without managing GPU infrastructure was genuinely valuable. The main improvement needed is documentation depth --- the API surface is larger than what the cookbook covers, and discovering available methods required exploratory debugging via \texttt{dir()} and \texttt{inspect.signature()}.
